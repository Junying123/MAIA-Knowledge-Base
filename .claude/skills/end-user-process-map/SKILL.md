# End-user & Process Map (Lens 3)

Produces the **End-user & Process Map** — the half of Lens 3 that sits beside the
UAT checklist in the Product Onboarding SOP (M3 → Gate 2). Answers *"how will MAIA
actually be used, by whom, step by step?"* so config (M6) and training (M9) build on
real users and real workflow, not assumptions.

Save to the client folder:
`03 - Clients/Active Cooking Clients/[Client]/[Client] — End-user & Process Map.md`
with standard KB frontmatter.

## SOP Definition of Done (Lens 3, the map half)
Done when: **real end users named + contacted** (sales / finance / logistics);
**order intake, documents, and step-by-step order-taking captured**. (The locked UAT
checklist is the other half — produced by the `uat-checklist` skill.)

## Sources — gather what you have
1. **Forensic Dossier** — actor decision map (B4), the client's world / operating flow (B3), commitments + authority ambiguity. *Primary for actors.*
2. **VoC Extraction** — actor register (named users + confidence), E2E workflow, priorities, coverage gaps (whose voice is thin/absent).
3. **Scope Lock** — what each role actually does in MAIA (locked items only); role isolation rules.
4. **Customer Narrative** — as-is workflow, order intake formats, customer types, documents, MAIA role.
5. **Role/permission files** — any `Role Permission/*.csv`, `* User Setup.xlsx` already in the folder.

If a source is missing, write `MISSING SOURCE: <name>` at the top and continue with
what you have. Never invent a person, contact, or permission.

## Core rule — identity gaps are marked, never guessed
The map's weakest point is always **people identity**. Where the sources do not name
or confirm a real person/contact, write **`NEEDS CLIENT INPUT`** — do not invent a
name, do not assume a role→person mapping. The value of this map is an honest picture
of who is (and isn't) confirmed, ready to close at the sign-off session.

## Output structure (produce in order)

### 1. Actor & Role Register
Table: `Actor (real name) | MAIA role (Sales / Finance / Logistics / Management / Admin) | Authority | Contacted? (YES / NO / UNKNOWN) | UAT signatory? | What they do in MAIA | Voice confidence (from VoC)`.
- Pull names + authority from the Forensic Dossier B4 and the VoC actor register.
- Flag every un-named or un-contacted role as `NEEDS CLIENT INPUT`.
- Name the **UAT signatory** explicitly — if unknown, that is the #1 gap (SOP M2/M8 require it).

### 2. Order-Intake Map
How orders actually arrive and get into MAIA. Cover: channel(s) (WhatsApp text / voice / forwarded / informal), language (e.g. Chinese/mixed), one-number vs many, who forwards, and the human-review-before-submit step. Ground in the Customer Narrative + VoC. Note must-NOT rules (e.g. voice note never auto-submits).

### 3. Document Flow
Table or diagram of the documents and their order, with the system-of-record boundary: `Document | Generated by role | Trigger | SQL/ERP constraint`. Cover SO, DO/DN, Invoice, Credit Note, Pro Forma, payment receipt — only those the client actually uses (per Scope Lock / Narrative). State the ERP-master boundary (MAIA sits on top; SQL stays master).

### 4. Step-by-Step Process Map (the spine)
The end-to-end order-taking flow as numbered steps, from order arrival to cash, marking **who** does each step and **where** (WhatsApp / web / ERP). Then a short **per-role swimlane** — what Sales, Finance, Logistics/Warehouse, and Management each do across that flow. Ground the spine in the VoC E2E + the confirmed workflow (e.g. draft SO → external pick → confirm weight → SO/DO/Invoice → push ERP → payment recon). Keep the client's real framing and examples.

### 5. Permission Matrix
Table: `Role | Can create | Can approve | Can view (own vs all) | Cannot do`. Ground in the Scope Lock role rules (e.g. sales isolation, credit-controller approval) and any role/permission file. Flag anything not confirmed as `NEEDS CLIENT INPUT`.

### 6. Gaps & Sign-off Agenda
List the `NEEDS CLIENT INPUT` items as a short agenda for the workflow/UAT sign-off session (per the Forensic Dossier's recommended move). Typically: UAT signatory, named warehouse user + driver, role→person roster, permission confirmation. Each line = one question that closes one gap.

---

## Method
1. **Actors first** — build the register from Forensic B4 + VoC; mark identity gaps immediately.
2. **Only map what's locked/real** — the process + documents follow the Scope Lock's locked items and the Narrative's real workflow; do not map deferred/AIP features as live.
3. **Preserve the client's concrete framing** — real roles, real order formats, real document names, real examples (weights, item names).
4. **Honesty over completeness** — a map full of `NEEDS CLIENT INPUT` on people is correct if the sources don't name them; that is the point.
5. **Cross-link** — reference the VoC, Scope Lock, and UAT checklist so the three product artifacts stay one system.
