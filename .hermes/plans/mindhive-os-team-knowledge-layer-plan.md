# Mindhive OS Team Knowledge Layer Plan

## Goal
Design a new team-facing knowledge layer that sits between Mindhive OS (Lark Base / Wiki / Docs) and MAIA CODEX, so Claude Code / Codex can reliably read, draft, validate, and publish PM artifacts without depending on Gareth's messy personal MAIA KB.

## Success Criteria
1. Product/team knowledge is split cleanly between operational state, long-form knowledge, and formal execution specs.
2. Agents can read from Lark, work locally in markdown, and push approved output back to Lark with minimal manual copy-paste.
3. Team docs for product scope, client narrative, account plans, and product/tech status follow fixed templates and ownership rules.
4. The new layer does not replace Mindhive OS or MAIA CODEX; it bridges them.
5. A new PM can find the current truth for any client/workstream in under 3 minutes.

## Non-Goals
- Rebuilding Mindhive OS from scratch.
- Turning personal MAIA KB into the team system.
- Letting agents directly mutate production truth without review gates.
- Building a mega-agent that owns every PM workflow.

## Core Problem
Current state is fragmented:
- Mindhive OS (Lark) holds live task / tracker / wiki state.
- MAIA CODEX is intended for formal specs.
- Personal MAIA KB contains useful thinking and templates but is messy and not suitable as team truth.

Result: agents have no clean shared workspace for drafting, reconciling, and publishing PM knowledge artifacts.

## Proposed New Layer
Create a new layer called:

**MAIA Team Knowledge Layer (TKL)**

It is a controlled workspace for team-facing PM knowledge, sitting between:
- **Mindhive OS** = live state / trackers / assignments / workflow status
- **MAIA Team Knowledge Layer** = curated working knowledge + narrative artifacts + reviewable drafts
- **MAIA CODEX** = formal product / feature execution specs for dev

## Architecture

### 1. Source-of-truth split

#### A. Mindhive OS (Lark Base / Wiki / Docs)
Use for:
- live task tracker
- product tracker
- client status
- due dates
- owners
- sprint / tech progress
- workflow state
- publishing destination for approved docs

#### B. MAIA Team Knowledge Layer
Use for:
- client narrative drafts
- scope summaries
- account plans
- PM working summaries
- meeting synthesis
- structured markdown versions of Lark content
- reviewable intermediate artifacts generated by agents
- reusable templates / schemas / prompts

#### C. MAIA CODEX
Use for:
- prd.md
- design.md
- tasks.md
- changelog.md
- any formal feature specification handed to dev / coding agents

### 2. Operating principle
Agents should follow this loop:
1. Read live state from Lark Base / Wiki / Docs via lark-cli.
2. Pull relevant artifacts into local markdown workspace.
3. Draft/update structured team documents in the Team Knowledge Layer.
4. Run validation against templates / completeness rules.
5. Publish approved content back to Lark.
6. Update tracker/status in Lark Base.
7. If scope becomes implementation-ready, generate / update MAIA CODEX artifact.

## Per-client file contract
Each active client folder should have at minimum:
- `README.md` — current snapshot
- `01 - Narrative/Current Client Narrative.md`
- `02 - Scope/Current Scope Summary.md`
- `03 - Account Plan/Current Account Plan.md`
- `05 - Risks & Decisions/Decision Log.md`
- `06 - Published Links.md`

## Document classes

### Class A — Live operational docs
Owned by Lark. Local markdown is a working mirror only.
Examples:
- task tracker summary
- delivery status digest
- account health digest

### Class B — Curated narrative docs
Owned by Team Knowledge Layer, then published to Lark.
Examples:
- client narrative
- account plan
- scope summary
- meeting synthesis

### Class C — Formal execution specs
Owned by MAIA CODEX.
Examples:
- PRD
- design
- tasks
- changelog

## Lark integration contract

### Lark Base should remain the structured state layer
Minimum entities to expose to agents:
- client master table
- product task tracker
- tech delivery tracker
- artifact registry
- decision log / milestone table

### Lark Wiki / Docs should remain the team reading layer
Approved documents get pushed here after validation.

### Local Team Knowledge Layer acts as the editable workspace
Agents should not draft directly in Lark when the document is non-trivial. They should:
- fetch source context
- draft locally in markdown
- validate locally
- publish back to Lark

## Agent workflow design

### Agent 1 — Lark Context Reader
Input: table/doc/wiki references
Output: normalized markdown / JSON context pack

### Agent 2 — PM Drafter
Input: context pack + template
Output: narrative / scope / account-plan draft

### Agent 3 — Validator
Checks:
- required sections present
- no contradiction with Lark Base status
- owner / next step / risk fields exist
- no unsupported claims

### Agent 4 — Publisher
Input: approved markdown
Output:
- update/create Lark doc or wiki node
- write published link back to registry
- optionally notify team chat

### Agent 5 — CODEX Handoff Agent
Trigger: scope approved / implementation-ready
Output: formal MAIA CODEX package or update request

## Governance rules
1. Personal KB is never the team source of truth.
2. Mindhive OS owns live status and assignments.
3. Team Knowledge Layer owns curated PM knowledge artifacts before publishing.
4. MAIA CODEX owns implementation spec truth.
5. Every published artifact must record:
   - source inputs
   - last updated
   - owner
   - review status
   - Lark URL
6. Agents may draft automatically, but publishing should pass a review gate for high-stakes docs.

## Suggested templates to define first

Deliverables:

- folder structure
- file naming rules
- 4 core templates
- publish/review rules

### Phase 2 — Build one real client pilot
Use one active client only.
Recommended pilot: Holsen or Fixguru.
Deliverables:
- client folder
- narrative draft
- scope summary
- account plan
- published links register
- Lark sync workflow tested end-to-end

### Phase 3 — Add Lark CLI workflows
Automate:
- fetch Lark doc/wiki into markdown
- update Lark doc from markdown
- read Base tracker rows into context pack
- write metadata / published links back to Lark Base

### Phase 4 — Connect to MAIA CODEX
When scope is approved:
- generate CODEX handoff package
- create/update `prd.md`, `design.md`, `tasks.md`, `changelog.md`
- link CODEX path back to Team Knowledge Layer and Lark Base

### Phase 5 — Expand to full team usage
Only after pilot works.
Add:
- more clients
- more templates
- more agents
- dashboards / digests

## Validation commands / checks
1. Lark auth works:
   - `lark-cli auth status`
2. User-scoped read works:
   - `lark-cli --as user wiki spaces get_node --params '{"token":"<node_token>"}'`
3. Docs fetch works:
   - `lark-cli --as user docs +fetch --doc "<obj_token>"`
4. Base read works:
   - `lark-cli base +record-search --base-token <token> --table-id <id> --format json`
5. Docs update works:
   - `lark-cli docs +update --doc "<obj_token>" --markdown "..." --mode overwrite --as user`

## Risks
- Team creates duplicate truth between Lark and local markdown.
- Agents publish bad drafts directly to Lark without validation.
- MAIA CODEX remains disconnected from PM artifacts.
- Folder structure gets overdesigned before one pilot workflow works.
- Personal KB habits leak into the team layer.

## Guardrails
- Mirror state from Lark, do not invent separate tracker truth locally.
- Only curated narrative docs live in the team layer.
- Keep local docs markdown-first and template-driven.
- Use one pilot client before team-wide rollout.
- Require linkback metadata between local doc, Lark doc, and CODEX spec.

## Recommendation
Build this as a **team-facing drafting and publishing layer**, not a replacement for Mindhive OS.

Correct stack:
- **Mindhive OS** = live operational state
- **MAIA Team Knowledge Layer** = curated PM knowledge workspace
- **MAIA CODEX** = formal execution spec repo

Anything else will become a messy fourth truth source and waste everyone's time.
