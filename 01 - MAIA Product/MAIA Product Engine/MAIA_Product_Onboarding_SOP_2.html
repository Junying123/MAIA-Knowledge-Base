Role Model — Doers vs Checkers

Owners are roles, not people — so the engine survives any one person leaving. A separate roster maps people → roles and can change without touching this document.

▍ Doers — the engine (Product)

Onboarding PM

Senior product doer
Owns the client end-to-end: relationship, scope lock, the quality gate, UAT sign-off, Tuesday update, and the customisation track per account.

Delivery PM ×2

Junior product doers

Process Engineer

Incoming · works with Head of Product

Product's Definition of the Client — 3 Lenses (at M3)
LENS 1

Scope Lock

"What do we owe to close this client?"
Done when: every item resolved to a status below; zero "needs scoping" (AIP allowed); client signed.
Scope statuses
Locked — confirmed, in this core build.
Implementation — confirmed, scheduled as a later customisation.
Superseded — replaced by a newer agreed decision.
Out of scope — explicitly excluded, client-acknowledged.
Agreement in principle — directionally agreed, detail pending. Allowed at lock.
Needs scoping — unresolved. Must be zero before sign.
LENS 2

Voice of the Customer

"What matters most — never lose sight of it."
Done when: the full complete narrative is present and the VoC extraction document is present — extracted from conversation + meeting transcripts and verified. Stands as the per-account north star for every build decision.
LENS 3

End-user & Process Map

"How will it actually be used — and how do we prove it?"
Done when: real end users named + contacted (sales/finance/logistics); order intake, documents and step-by-step order-taking captured; and a locked-in UAT checklist with all test cases defining how each user will use the system. Product defines this checklist upfront — it is the proof of full clarity on the end goal.

Always-Do Standards — The Weekly Heartbeat
📋 Every Monday — Account Grooming
For every account, each PM must be hyper-clear on 4 things. This feeds Tuesday and surfaces slippage before it becomes a fire.
1.Current state — where the account actually is right now.
2.Milestones — with date clarity (target vs actual).
3.Blockers — with date clarity (since when, until when).
4.Next action — named, for each of Client / Product / Tech / Sales.
Sample outline — grooming entry (internal){Client} — {current milestone} ① State: {one line — where it actually is} ② Milestone: {next} · target {d} / actual {d | on-track} ③ Blocker: {what} · since {d} · needs {who} by {d} ④ Next action Client → {action / date} Product → {action / date} Tech → {action / date} Sales → {action / date}
📅 Every Tuesday — Client Status Update
Sent to the client. Progress last week · open items needing action (with owners) · next-week plan with important dates locked in.
Standard: an easily digestible, readable, actionable message sent directly into the client WhatsApp group — not a buried doc.
Sample outline — Tuesday WhatsApp update[MAIA] {Client} · Weekly Update — {date} ✅ Progress (last week) • {what shipped / milestone hit} 🔧 Needs action • {item} — {owner} — by {date} 📅 This week • {milestone} — target {date} 📌 Locked dates • UAT {date} · Go-live {date}
★ This is a promise — it does not slip
Every client meeting → summary within 24h: findings, learnings, feedback/blockers, action points with owners and dates.
Deploy Core MAIA first, always. Customisations scheduled on separate dates later — PM owns their scope, timeline and risk under the same account.
Every artifact lives in the account workspace. Nothing important sits only in a person's head or DMs.
Every scope decision cites its source (transcript / SOW / kickoff note) — no laundering of unconfirmed assumptions into the lock.
No self-approval on QA. One runs, a different person countersigns.
Client comms flow through the Account/Onboarding PM — one voice to the client.

Seam Rules — Where It Breaks
Rule A · Feasibility ≠ commitment
Tech leads assess feasibility in the room but never commit scope there. Feasibility is an input; scope is only locked in the scope-lock doc.
Rule B · Recon before the client sees it
Sales↔product reconciliation happens before kickoff. The lock is run through as a reconciled artifact — never the moment a gap is discovered.
Rule C · Internalise blockers, validate early
Pull dependencies in-house where we can — WABA + hosting done; integration sandbox (Opt 2) next. No integration-dependent work starts until the path is validated as connecting.
Rule D · Escalation is rare and pre-defined
Only fixed triggers reach founders (see each card's escalate line). Everything else has a standing rule the PM executes alone — that's what keeps management out of the engine.

The document is not the goal — a demonstrated smooth run is.
