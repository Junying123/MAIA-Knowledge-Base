Invoice & CN — Payment Terms Visibility + Payment History Display
MAIA · Phase 1 · Backend + PDF + Frontend
The problem in one sentence
MAIA currently shows clients a number. This feature makes it show clients a story — what was agreed, what has been paid, what is due now, and what is coming next. All from one document, automatically, without Finance having to explain it manually every time.
Three problems we are solving
1
Invoice only shows a grand total — clients have to call Finance to know what to pay
When a deal has instalment terms (e.g. 20% now, 60% in 30 days, 20% in 60 days), MAIA knows the schedule internally but never surfaces it. The client receives an invoice showing only RM50,000 total. They call Finance to ask "how much do I pay today?" Finance manually does the math. This happens every single invoice, every payment, every client.
2
Payments already made are invisible on the invoice document
When Finance records a payment against an invoice, that payment never appears on the invoice document itself. The client has no way to see what they have paid, when they paid it, or what they still owe — without calling Finance again. There is no self-service payment history.
3
Overdue status in the invoice list is wrong for multi-term invoices
The invoice list derives overdue status from the header due_date field — which on multi-term invoices is set to the last instalment date (Day 60). This means if a client never pays the CIA term on Day 1, the system shows the invoice as "Unpaid" (not overdue) for 60 days. Finance has no system alert that money is already late.

What we are building — four changes
1 — Invoice PDF and detail page
Three new sections added in fixed order: Summary block extended with Total Received / Outstanding / Due Now · Payments Received table (one row per payment, omitted if no payments) · Payment Schedule table with Allocated / Balance / Status columns per term row. Overdue rows are visually distinct. All figures computed server-side at render time — never cached.
2 — Invoice list overdue status fix
The listing API now derives overdue status from payment schedule term rows, not the header due_date. A CIA term that's been unpaid since Day 1 shows as Overdue immediately. New status set: Draft / Unpaid / Partially Paid / Overdue / Paid / Cancelled. Overdue takes priority over Partially Paid. Paid takes priority over all.
3 — Payment terms inheritance (QT → SO → SI)
Payment terms agreed at quotation stage now flow automatically to the Sales Order and then to the Sales Invoice at create time. Finance no longer re-enters terms manually on every invoice. Both QT→SO and SO→SI paths are confirmed working via MAIA's custom APIs and ERPNext core.
4 — Payment Term doctype extension
Two new fields added to the Payment Term master: term_type (standard / advance / on_delivery / immediate) and is_advance_payment (boolean). These fields let the system compute due dates and statuses deterministically — without guessing from term names. bench migrate auto-populates all 52 existing records with the default value.
Who benefits and how
Finance / AR staff
No more manual "how much do you owe today" calculations. Invoice is the single source of truth. Overdue invoices surface immediately in the list — no more hidden late payments for 60 days.
Client
Opens one document and understands everything — what was agreed, what they have paid, what is overdue, what is coming. No need to call Finance.
Business owner
Accurate overdue reporting from Day 1 of any unpaid term. Faster cash collection. Clean accounting — terms agreed at QT flow through to the invoice without manual re-entry.

How values are computed
// payment_schedule is optional on invoices // if null → skip all computation, return payment_schedule: null // if rows exist → compute due_date per row using term_type: term_type == "advance" | "immediate" → due_date = posting_date term_type == "standard" → get_due_date_from_template() term_type == "on_delivery" → invoice.items[].delivery_date (all items must share same date) // term_type field added to tabPayment Term with default = "standard" // bench migrate auto-populates all existing records with "standard" // Finance updates non-standard terms (advance/on_delivery/immediate) via UI // term_type == null is therefore not reachable after migration // FIFO allocation sort term rows by due_date ASC for each row (earliest first): allocated = min(remaining_received, row.payment_amount) balance = row.payment_amount - allocated remaining_received -= allocated // status per row balance == 0 → "Paid" due_date < today AND balance > 0 → "Overdue" due_date == today AND balance > 0 → "Due" due_date > today AND balance > 0 → "Pending" on_delivery AND balance > 0 → "Pending (On Delivery)" // summary values total_received = SUM(tabPayment Entry Reference.allocated_amount) WHERE reference_name = invoice.name AND pe.docstatus = 1 outstanding_balance = MAX(0, grand_total - total_received) amount_due_now = SUM(balance WHERE due_date <= today) credit_on_account = SUM(pe.unallocated_amount) WHERE pe links to this invoice AND total_received > grand_total

How payment_status is computed
// post-query enrichment — 2 batch queries after main SELECT Batch 1: fetch tabPayment Schedule rows for all SI IDs on this page ORDER BY due_date ASC Batch 2: SUM(allocated_amount) FROM tabPayment Entry Reference WHERE reference_name IN (si_ids) AND pe.docstatus = 1 GROUP BY reference_name // FIFO compute amount_due_now per SI (same as detail API) // then derive payment_status: docstatus == 2 → "Cancelled" outstanding_balance == 0 → "Paid" any term: due_date <= today AND balance > 0 → "Overdue" total_received > 0 AND outstanding > 0 AND no overdue terms → "Partially Paid" no payments AND no overdue → "Unpaid" docstatus == 0 → "Draft" // fallback — no payment_schedule rows if payment_schedule is empty: if due_date <= today: payment_status = "Overdue" else: payment_status = same as existing status field // note: amount_due_now, outstanding_balance, payment_status // are NOT sortable — post-query computed, not in base SQL
payment_status values
Paid Overdue Partially Paid Unpaid Draft Cancelled
Overdue takes priority over Partially Paid. Paid takes priority over all non-Cancelled states. The existing status field is unchanged — both are returned. Frontend should display payment_status in the list view status column.

Terms are shown as-is from the child table — no FIFO computation, no enrichment. Explicitly excluded in intake spec.
Debit Note (DBN) — all new sections explicit DBN (is_debit_note = 1) is fully excluded from all new sections — Payment Terms, Payments Received, Outstanding, and Due Now are all hidden entirely. Explicitly excluded in intake spec.
Automated payment reminders and dunning workflows explicit No automated overdue notifications, reminder emails, or dunning logic of any kind. This feature only surfaces payment status visually — it does not trigger any actions based on overdue state. Explicitly excluded in intake spec.
Per-term payment allocation in the data model explicit FIFO allocation is a display-layer computation only. No write-back to tabPayment Schedule or tabPayment Entry Reference. allocated_amount and outstanding on the schedule rows remain untouched. Explicitly excluded in intake spec.
Changes to Payment Entry creation flow explicit No changes to how Payment Entries are created, allocated, or submitted. The existing PE flow is consumed read-only by the new computation service. Explicitly excluded in intake spec.
Enforcing single-invoice-per-order explicit Both practices remain supported — single SI covering the full order, and multiple partial SIs per order. No validation or enforcement is added to restrict either pattern. Explicitly excluded in intake spec.
