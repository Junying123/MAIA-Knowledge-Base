Manufacture Stock

One-shot "make finished goods from raw materials" call. A single request creates the production paperwork and moves stock — the caller never orchestrates Work Orders or Stock Entries themselves.

⚙️ What it does

  • Explodes the BOM recipe and scales raw-material quantities to the requested qty.
  • Checks raw-material availability in source_warehouse atomically before touching anything.
  • On success, creates a Work Order (with skip_transfer=1) and a "Manufacture" Stock Entry in one transaction.
  • Returns the names of both documents and the full consumed / produced ledger lines.

🛑 What it does not do Guardrails

  • No partial production — it's all or nothing. If any raw material is short, nothing moves.
  • Not idempotent — two identical successful calls create two stock movements.
  • No dedup / auto-retry — check for an existing Stock Entry before retrying a timed-out call.
  • All raw materials must be in a single source_warehouse — no per-component sourcing yet.
Flow: raw material source_warehouse ──▶ BOM recipe (explode + scale) ──▶ finished-good stock target_warehouse. Under the hood this is a Work Order with skip_transfer=1 + one Manufacture Stock Entry. The caller sees only the resulting names and ledger movements.

Pydantic validation list — map back to form fields

HTTP error codes

  1. 422 — Missing or invalid field (e.g. qty ≤ 0, missing warehouse).
  2. 404 — item_id, bom_no, company, or a warehouse doesn't exist.
  3. 422 — Business rule broken: item not MANUFACTURED, BOM not submitted/active, group warehouse, wrong company, no default BOM.
  4. 422 — Ledger rejected (e.g. race caused negative stock).
  5. 401/403 — Missing or invalid token / no permission.
  6. 500 — Unexpected server error.

Shape: { "error": "…", "message": "…" }. Validation failures also include errors[].

Integration Notes

Frontend & Chatbot guidance

Single call, three outcomes. Collect the four required slots then fire once.

🖥️ Frontend

  • Form collects: finished-good item, qty, source warehouse, target warehouse. BOM optional — leave blank to use the item default.
  • On status: "success" — confirm the run, show work_order and stock_entry as links, render consumed/produced lines.
  • On status: "insufficient_stock" — render shortage table. Don't treat as an error toast — it's actionable.
  • On HTTP error — surface message; for 422 Validation error map errors[] back to form fields.

🤖 Chatbot

  • Collect four slots conversationally: item_id, qty, source_warehouse, target_warehouse. Ask for bom_no only if the item has multiple BOMs.
  • Confirm before firing — this moves real stock. State the item, qty, and warehouses before the call.
  • Never silently retry — a timed-out call may have succeeded.
  • On shortage, offer: "Want me to check where that stock is, or reduce the quantity?"
Atomicity guarantee: on insufficient_stock nothing is created. If the Stock Entry fails after the Work Order exists, the Work Order is rolled back — no orphan documents. Availability is checked point-in-time; native stock validation still guards against negative stock from a race.
